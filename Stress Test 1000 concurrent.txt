Here is the exact timeline of the visual illusion you are seeing:

1. **The Backend Batch Win:** Your Redis drain loop runs on a set interval (e.g., once per second). If your rate limit allows multiple users to pass through at once, the drain loop pops Users 5 through 9 in the *exact same transaction*. In Redis, User 5 and User 9 both officially become "WON" at the exact same time.
2. **The Frontend Polling:** The frontend dots don't know they won yet. They have to wait for their `setTimeout` to fire to ask the server for their status.


3. **The Jitter Math:** Because you intentionally added a random `jitter` of ±300ms to the poll interval, User 5 might randomly get a poll timer of `2000ms + 250ms = 2250ms`. User 9 might get lucky and get a timer of `2000ms - 250ms = 1750ms`.


4. **The Visual Illusion:** User 9's timer fires half a second earlier than User 5's timer. User 9 sends the fetch request, the server says "Yes, you won!", and the dot turns green visually. Half a second later, User 5 asks, gets the exact same answer, and turns green.



### 🛠️ The Verdict

This is not a flaw in your queue architecture. Your backend accurately processed them in strict chronological order. What you are seeing is just a **network polling race condition** on the frontend.

In fact, adding `jitter` to polling loops is an industry best practice! If you didn't have that jitter, all of your simulated users would hit your server with a `/status` request at the exact same millisecond, creating a mini DDoS attack. The jitter smoothly spreads the network requests out over time.
